# Як ми працюємо

## Git і pull requests

Є лише одна гілка: **`main`**. Комітити в неї напряму не можна, усі зміни потрапляють туди **тільки через pull request**.

1. На кожну задачу створюємо гілку від свіжого `main`: `<трек>/<issue>-<коротко>`, напр. `vision/12-board-homography`.
2. Відкриваємо PR у `main`. PR маленький (орієнтир до ~400 рядків(або як пощастить)), в описі пишемо `Closes #12`,
   тоді issue закриється сам після merge.
3. Merge можливий лише після зеленого CI і **мінімум 2 approve** від інших людей. Зміни в
   [інтерфейсах між модулями](architecture.md#модулі) (спільні типи — `common`) схвалюють власники обох модулів.
4. Merge: **Squash and merge**.

> Обов'язкові PR забезпечує захист гілки `main` на GitHub (Settings → Branches): «Require a pull request
> before merging» з 1 approve і «Require status checks to pass» (CI).

## Тікети

- **Назва** — коротка й лаконічна, лише суть задачі, без подробиць реалізації. Напр. `Main & Orchestrator concept & skeleton`.
- **Опис** — 1–3 речення на початку тікета: що зробити й навіщо. **Без заголовка** «Що зробити».
- **`## Acceptance Criteria`** — короткий список пунктів, які **рев'ювер може реально перевірити**: команда запускається
  й дає результат, файл чи клас існує, тест проходить у CI, розділ документації написано. Без розмитих пунктів на
  кшталт «добре працює».
- **`## Context`** — лише якщо справді потрібен: 1–3 посилання на конкретні документи чи тікети й навіщо вони.
- **Тікети тримаємо в актуальному стані.** Якщо рішення змінилося (інший підхід, інша назва, інше залізо), тікет
  підправляємо під реальність: назву, опис, Acceptance Criteria. Застарілий тікет закриваємо з коментарем, чому.
- Шаблон: [`.github/ISSUE_TEMPLATE/task.md`](../.github/ISSUE_TEMPLATE/task.md).

## Документація: що де

| Що | Де |
| --- | --- |
| **Зовнішній опис** компонента: що робить, навіщо, з чим пов'язаний, як ним користуватися | `docs/*.md`; в [architecture.md](architecture.md) — згорнутий підпункт на кожен компонент |
| **Деталі реалізації**: як влаштовано всередині, кроки, обмеження | docstring у самому файлі коду (модуль, клас, функція) |
| `README.md` у теках коду | 1–3 речення й посилання на `docs/` |
| Чому ухвалено рішення, які були альтернативи | [decisions/](decisions/) (ADR) |
| Вимоги до компонента: **FR** (що робить) і **NFR** (як: обмеження реалізації), пронумеровані `FR-…`/`NFR-…` | [requirements/](requirements/), файл на компонент |

Довгі списки й визначення в документах — у згорнутих блоках `<details>`, щоб сторінку можна було переглянути одразу.

## Код

- **Рядки з підстановкою значень — лише f-рядки** (`f"..."`), зокрема в логах: `log.info(f"{name}: створено")`,
  а не `log.info("%s: створено", name)` чи `"{}".format(...)`. Так зрозуміліше, що й куди підставляється.
  Виняток — шаблони, які заповнює сама бібліотека, напр. формат рядка логу `"%(asctime)s %(message)s"`.
- **Усе, що виводить програма, — англійською:** лог, повідомлення про помилки, `--help`, вивід скриптів. Коментарі,
  docstring і документація — українською.
